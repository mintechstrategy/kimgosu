## 1. 결론과 우선순위

P0 내부정정: 원안의 D2 자기신고→리뷰 진입을 SCOPE의 양측 합의/완료확인 조건으로 대체하지 않는다. F5의 '모든 채팅도 사라짐'은 상대방 대화 조회 및 재가입자 비복원이라는 원래 기능정의에 맞게 정정 대상으로 반환한다. 이 두 원안의 유지 여부를 사용자에게 다시 묻지 않는다.

P0 증거정정: engineering의 screen-evidence.visibleText는 브라우저에서 관측한 visible DOM이 아니다. D2/F5 HTML에는 추출된 옛 문구를 바꾸는 스크립트가 이미 있다. 따라서 '현재 렌더가 리뷰 잠김/모두삭제를 보여 준다'는 결론은 이번 증거로 성립하지 않는다. 실제 DOM·PNG·runtime 관측은 하지 않았다. 정적 본문·설명·SCOPE의 모순은 여전히 정정 대상이다.

P0 보완: 프로필사진은 원안 기능인데 member/expert에 현재 선택 사진의 연결이 없다. 이는 새 기능을 넣을지 묻는 정책이 아니라 기존 요구를 충족하기 위한 논리모델 보완이다. 동의문 실제 본문·버전과 CS/원장/채팅의 서버 권한은 미확보·미검증이다.

P1 정책제안: 고수 사전심사 강도, 반복 리뷰/방 유일성, 견적 하트의 데이터 의미, 검색 저장 위치·지표 집계 단위·운영 책임은 미채택 선택지로만 반환한다. CARD22 제출 3뷰의 시각 승인과 새로운 견적찜 기능 승인은 다르다. 승인된 3뷰와 Swift 시험은 재실행하지 않았다.

기존 26개 gap의 개별 분류·근거·다음 담당은 RESULT.json.gapReviews가 정본이다. 이전 미매핑 9개는 같은 파일의 oldUnmappedReviews에서 별도 판정했다. 빈 매핑이 없어졌다는 이유로 139뷰 적합이나 DB 승인 완료로 승격하지 않는다.

## 3. 핵심 대조와 내부정정

### 3.1 D2·D3: 자기신고와 양측 합의를 분리

원문 O:953–957 / D2_1 node 42:466: 리뷰 남기기에서 거래 여부 질문, '네'면 D3, 거래 여부 DB 보관, 의뢰인/전문가 한 명이라도 거래했다고 하면 다음 진입의 질문 생략이다. 이것은 자기신고이며 지급·완료 검증이 아니다.

SM:4652–4727 및 10483–10558은 any true와 자기신고 저장 성공을 구분해 원안에 가깝다. 단, SQL이나 저장 실패 처리의 실제 동작 증거는 없다. 반복 거래의 리뷰 단위·응답 변경/철회·중복 단위는 원문으로 결정되지 않았으므로 U02로만 제안한다.

중요 반증: SE:2885,2955–2976에는 리뷰 잠김/거래 미확정이 남지만 H/D2.html:77은 실행 시 텍스트를 '리뷰작성'으로 바꾸고 TRADE_CONFIRM으로 연결하며 pill-note를 제거한다. 따라서 G-D2-REVIEW의 '시안이 잠김'은 정적 본문 수준의 발견으로 한정해야 한다. 실행 성공·최종 표시를 직접 확인한 것은 아니다(NF-009-01).

### 3.2 F5: 본인 접근 종료와 상대방 대화 조회

O:1640–1645 / 49:5175의 포괄 안내와 O:1669–1674 / 49:5205의 구체 기능정의가 충돌한다. 구체 정의는 상대방이 대화를 조회할 수 있도록 삭제하지 않고, 동일 소셜 재가입자에게도 과거 대화를 복원하지 않는다고 명시한다. S:66,271–275도 이 구분을 이미 인식했다.

## 4. 새 발견: 기존 26 gap과 별도

## 5. 미채택 선택지·권고와 영향

U04 개인정보·운영 접근: 데이터 종류별 처리 근거/정리·백업/재가입/원장·CS·감사 범위와 열람 승인분리·신고대상을 묶어 사업자·전문 담당과 결정한다. 최소권한·사유·필요 구간·감사 실패시 차단이 권고다. 무제한 보관/즉시 전부삭제/임의 TTL 숫자는 채택하지 않는다. 기간별 저장·정리·감사 운영비가 다르고 권리처리·분쟁 증거 유실/과다보유 위험이 있다. 합법·안전하다고 판정하지 않는다.

POST_UNAVAILABLE: 숨긴 본문 조회/삭제쓰기 없는 안전 안내는 타당하다. A5/A3_SERVICE 고정 복귀 때문에 견적 호출까지 해결됐다고 할 수 없다.
POST_SAVE_ERROR: 실제 서비스 수정 실패폼 문맥이다. 새 테이블이 불필요하지만 generic 이름만으로 견적 오류에도 같은 내용/복귀를 적용하지 않는다.

각각의 정확 SM/SE 행, 잔여 조건, 다음 담당은 RESULT.json.oldUnmappedReviews에 있다. 9개 분류 처리는 기능·runtime 해결과 다르다.

## 8. 실제 실행 검증·실패·NOT_RUN

실행한 것은 read_file/search_files의 실제 반환에 근거한 문서·원문·선택 ID/컬럼·스크립트 대조와 이 디렉터리 문서 작성이다. 별도 사용자 조사/시장 수치/요금 조회·법률 검토는 수행하지 않았다.

도구 차단: deferred 검색 terminal/python 및 execute/shell 모두 결과0, 연결 도구는 todo 하나뿐이었다. 따라서 stdlib JSON 키/ID 추출·SHA256 재계산·config stat·git status/branch·검증 스크립트 실행은 할 수 없었다. 설정이나 프로필을 바꿔 우회하지 않았다. 대용량 SM/SE는 전체 출력 없이 ID 위치 검색 후 필요한 행만 읽었다. 이것을 stdlib 실행으로 보고하지 않는다.

실패 보존: 최초 추정 projects/kimgosu/product/SCOPE-v0.2.md 조회는 not_found였고 B:203의 실제 S 경로로 복구했다. product 디렉터리 최초 검색은 존재하지 않았으며 새 허용 폴더만 작성했다. O 첫 복합 검색은 '[Errno 3] No such process'였고 단순 node 검색과 구간 읽기로 복구했다. 넓은 파일 검색은 무관한 디렉터리를 반환해 증거로 사용하지 않았다.

B:9의 fileCount606, B:618–640의 4개 config metadata와 읽기금지 조건은 확인했으나 현재 시작/종료 파일 해시·stat 일치 여부는 NOT_RUN이다. 원래 008의 보호587/설정2 통과를 이번 606/설정4의 통과로 재사용하지 않는다. 설정 내용/비밀값은 읽지 않았다. 이 한계 때문에 상태는 partial이다.

NOT_RUN: stdlib 추출/자동 coverage equality, baseline606 전후 hash·config4 metadata 대조, native 환경/현재 git 확인, 139 전체HTML 재파싱·실행 DOM·CARD22 PNG/원본/ERD 시각, Swift/앱 재검증(재실행 금지), 실제 DB/SQL/DDL/migration·원격 API·다중사용자 채팅·업로드·CS 송신·동의/지표/권한/경합 fixture 시험, 법률상 안전/보관기간/합법성 확정, 외부 발송·Telegram·배포. 기존 시험 결과를 본인 실행으로 보고하지 않는다.
