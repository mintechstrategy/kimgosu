## 사용자 흐름 기준선

1. **탐색:** 홈 → 카테고리 선택 → 대면 서비스이면 위치 설정 A2 → 서비스 리스트 A3 → 서비스 A5 또는 견적 A4 상세. 검색 B1은 일치 카테고리가 있으면 리스트로, 없으면 연관 추천 B2로 분기한다. 근거: 새로 제공된 `서비스순서도.png`의 A1–A5, B1–B2.
2. **소비자 요청:** 카테고리와 요구사항을 입력해 견적 요청을 게시하고, 받은 제안 또는 서비스 상세에서 고수와 대화를 시작한다. 화면 근거: C1, D1–D2.
3. **고수 활동:** 고수 서비스를 등록·관리하고 자격이 맞는 견적 요청에 제안한다. 제안 자격에 같은 카테고리의 등록 서비스가 필요하다는 내용은 화면 근거이며, 전문성 인증 정책은 미결정이다. 화면 근거: A3–A5, F2–F3.
4. **상담:** 서비스/견적 등 연결 대상과 분리된 채팅방에서 메시지·첨부·읽음 상태를 관리한다. 구현 계약은 [채팅 API](../CHAT-API.md)를 따른다. 화면 근거: D1–D3; 독립 도메인은 사용자 확정 지시.
5. **후속 활동:** 거래 여부 표시와 리뷰 화면이 있지만, 거래의 법적·업무적 의미 및 리뷰 자격은 미결정이다. 화면 근거: D2–D3.
6. **진입/인증:** 순서도상 등록·채팅·마이 탭에는 로그인 분기가 있고, 카카오/네이버 로그인 E1에서 최초 가입일 때만 약관·SMS 인증 E2로 간다. 근거: `서비스순서도.png`. 재진입 동작은 미결정이다.

## 설계 및 구현 상태

- 구현됨: FastAPI 채팅 API, 서비스 독립 `chat_subjects` 관계, 2인 채팅, 메시지·첨부·읽음, WebSocket/Redis 이벤트, JWT 참여자 검사. [채팅 계약](../CHAT-API.md) 및 `app/chat/`, `migrations/versions/0002_chat.py`, `0003_chat_attachments.py` 참조.
- 구현됨: Docker Compose 배포 구성과 GitHub Actions 기반 CI/CD 및 로컬 배포 에이전트. 현행 배포 절차는 [DOCKER.md](../../DOCKER.md) 참조.
- 구현됨: Android 디버그 앱의 브랜드 스플래시, 정적 A1 홈, 5개 탭 독바. 간편회원가입과 홈 데이터/API 연동은 이번 범위에서 제외. [Android 빌드 문서](../../mobile/README.md) 참조.
- 미구현: 회원가입·인증 발급, 카탈로그, 서비스, 견적, 제안, 알림, 거래·리뷰 등 전체 [API 초안](../API-SPEC.md)의 나머지 업무 기능.
- 주의: API 초안의 채팅 경로·메시지 필드·WebSocket 방식에는 초기 제안이 남아 있다. 실제 클라이언트 연동은 [채팅 API](../CHAT-API.md)의 구현 계약을 기준으로 한다.

## 다음 설계 순서 제안

고수 관점의 사용자 여정과 화면 목록을 보완하고, 계정/프로필 → 서비스/견적/제안 → 거래/리뷰 정책을 결정한다. 각 정책이 확정되면 데이터 모델과 API 계약을 순서대로 갱신한다. 우선 결정할 항목은 [DECISIONS.md](DECISIONS.md)에 기록한다.
